# Nonproduction delivery acceptance and approval packets

Source implementation, controlled verification and selected operational acceptance are separate.
The implementation authorization covers source PRs and their checks/merges. It explicitly excludes
an Exacly runtime delegation, public releases, production deployment, repository-rule changes and
new paid infrastructure. This plan requests none of those effects by itself.

## Available evidence and missing selections

The Exacly repository and its supported Linux CI establish source verification. Controlled tests
already use real private filesystem registries, fixed owning-workflow subprocesses, actual HTTP
measurements, process kills and concurrent generation contenders. They are reproducible reference
verification, not an independently approved operating environment. Do not relabel those fixtures or
their temporary approvals as live acceptance.

Before an operational packet can be finalized, select:

- An existing nonproduction GitHub repository and protected base supporting the exact merge
  profile, required checks/review policy and a narrow installation actor. The existing Exacly
  repository's force/deletion-only policy does not establish that profile. Do not change rules to
  make the trial pass.
- An approved persistent Linux host with local POSIX storage for the private publisher and static service,
  exact application/environment, owning workflow, prebuilt artifact producer and verifier.
- The trusted observer configuration/key and its actual administrative trust boundary. Local
  HMAC purpose separation does not establish independence from a dishonest same-user host.
- The independent reviewer/approval channel, credential minting/bootstrap procedure, finite
  trial budgets, expiry and ownership of retained recovery evidence.

No compatible operational destination or runtime grant has been supplied. Publication/deployment
reference trials need no public registry or paid service; GitHub acceptance still needs an existing
compatible repository. If a prerequisite is unavailable, keep that acceptance blocked and continue
independent source work.

## Assemble the exact packet before requesting authority

Freeze the installed artifact and source commit after full supported CI, and generate pins from
that actual installation. A new protected code/model/runtime revision requires a newly reviewed
pin; historical pilot approvals and successful test reports are not standing delivery authority.
For each stage, evaluate its selected prerequisites against the exact approved model and current
evidence. A prerequisite that depends on the first target's unverified live contracts stays blocked;
neither this reference profile nor its controlled tests supply that missing acceptance.

Retain the following exact documents with a content manifest, excluding token/key bytes:

1. Original objective/goal, immutable planning revision if selected, approved model/criteria/bindings
   and observer identities, actual installed adapter/runtime profile and selected producer proof.
   Pin the controller and owning publisher as separate runtime roles. Retain the fixed owner's
   read-only runtime-probe output, verify its digest from its measured body, and seal that pin in
   the independently reviewed owner configuration; do not substitute the controller's ambient
   process profile. The signed publication receipt retains the actual owner role identity.
2. Newly initialized canonical delivery journal path/UUID and original aggregate/native limits.
   Keep the same journal and original-goal counters across the approved delivery sequence; do not
   create a replacement store or rename a policy to reset capacity.
3. Exact requests, native payloads, policies/configurations, artifact sizes/digests and source/build
   identities. Private key descriptors and directory/registry/owner UUIDs identify actual storage;
   observer keys must use a separate namespace and lock domain from owner storage.
4. Separately reviewed per-stage authority, issuer/approval identity, validity window and the
   approval digest selected outside its JSON. The private publisher's one-version predelegation
   is additional to engine accounting; it is not a proof of an engine ApprovalPin or reservation.
5. The finite positive and negative operations, allowed exact refs/versions/generations, expected
   effects, observation windows, post-effect discovery, withdrawal and offline recovery commands.
   Account for preparation, conditional writes and all bounded owner/HTTP reads; full ceilings are
   charged before calls, not refunded from ambiguous outcomes.
6. Existing branch/tag automation that the selected refs can trigger. Any consequent owning
   workflow must already be within the approved nonproduction scope. The merge grant itself
   supplies no release/deployment authority; do not alter existing workflows to evade that boundary.

An unsigned template, matching digest or fixture issuer string does not prove human approval.
The selected independent reviewer approves the exact packet before its runtime invocation. Routine
steps already enumerated within that grant need no repeated approval; changed scope needs a new
applicable decision.

## Bounded merge acceptance

Use a canary pull request in the selected existing repository. Retain exact numeric repository and
actor identities, base `B`, head `H`, GitHub-generated merge `M`/tree, marker ref/key and protected
Git-blob inventories. Capture required checks and independent reviews for those identities. The
policy explicitly selects GitHub's current server-protection semantics and trusted administrator
stability during the call; it does not promise a check-conclusion or policy-version CAS.

Run one approved positive merge and inspect the actual merged PR, commit, authenticated marker and
receipt. Repeat exact historical access offline with unavailable current credentials/configuration;
it must return the retained receipt without provider calls or another write.

Separately enumerate genuine provider-negative probes for changed head, changed base and missing
required checks/reviews, including a concurrent no-op-head-lease rejection. A preflight-only rejection
does not prove the provider's atomic lease behavior. Verify the conditional transaction did not move
the base or create its marker on rejection. Keep these probes in their approved canary refs and
finite budgets; there is no permission to weaken a policy, dismiss reviews or move arbitrary refs.

Retain an uncertain/lost-response case and discover it without another mutation. A missing marker
never grants resend. If a credential expires, prepare the separately pinned read-recovery decision
for the original intent/journal/profile and zero writes. The genuine read-only merge observer can
verify a positive retained effect; that alone does not cover the negative provider cases above.

## Exact-byte publication and static runtime acceptance

Select two already built opaque artifacts, their approved independent verification and two new
immutable versions. The manifest fixes the bytes, source, owner workflow, registry UUID and package.
The existing package release workflow is not repurposed. Use the fixed `delivery publish` preview
to inspect local scope, then invoke only its separately approved effect. Retrieve the actual
published bytes with the authenticated consumer and require exact inventory/source/verification
meaning. Existing versions, altered bytes or foreign-intent receipts must not become a new success.

Start the independently configured nonproduction static service and select its actual generation.
Preview and separately invoke `delivery deploy` with the exact published artifact. Retain durable
intent, conditional generation change, authenticated activation, actual HTTP report and the native
generation/time point used for readiness. The observer checks served bytes, status, latency, source,
rollout, nonce, sample count and evaluation window. Verify a replacement supersedes the former
generation's applicability and expired observations never become fresh through presentation.

Create an independently approved, observable unhealthy condition in that environment. A known
deployment effect must remain recorded while operational readiness is unhealthy/unknown. No implicit
rollback follows. If the packet separately permits rollback, bind its exact current rollout,
fresh failure, allowed prior published artifact and remaining original rollback capacity. Invoke
`delivery rollback` once, verify its new generation and obtain new measurements. A second attempt
must not refill or exceed the original rollback limit.

Run finite negative cases for wrong environment/artifact/producer/contract, stale generation,
expired authority/report and unavailable observation. Retain partial files, actual effects and
recovery decisions. Do not clear an unresolved owner intent or infer safety to resend from absence.
Historical inspection remains offline; a fresh live API read needs its own applicable authority,
bounded deadline and accounting. Retained presentation must not silently perform unbudgeted reads
or advance its recorded environment-observation time.

## Retained evidence and closure

Keep each approval manifest, journal original scope/counters, exact payloads, native and common
receipts, actual inventories/rollout chain, observer reports, rejection results, source/CI identities
and recovery instructions in the selected protected retention location. Do not include credentials.
Record each requirement's source, controlled verification and operational acceptance separately.

REQ-041–043, APP-025, INFO-014 and CAP-005/PROC-005 stay proposed until the complete selected
contracts and authentic acceptance justify activation. The first target's REQ-037–039 remains
separate. Never copy a controlled pass into a live claim or hand-edit observed model state; use the
supported producers and CI/tooling for any subsequent observations.
