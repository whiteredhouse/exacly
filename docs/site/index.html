In Exacly, a requirement connects to the process it supports, the outcome it serves and the systems that implement it. Follow those links before changing the code.

Describe intent＋

Write outcomes, requirements, systems and their relationships in YAML. Review intent in the same pull request as the change.

observe:
  tests:
    workflow: .github/workflows/ci.yml
    cases: ["tests/reminders/*"]
Observe tests＋

In CI, read the bound test results. Record what passed, failed, was skipped or did not run. Keep the reference to the evidence.

exacly refresh spec/exacly \
  --context ci --state reports/state/ci.json \
  --junit reports/junit.xml \
  --revision "$GITHUB_SHA"
Check evidence＋

Ask what remains unverified. Assess a specific implementation and evaluate the readiness policy your team defines.

Passing tests and observed delivery are separate facts.

Missing evidence stays unknown.

Skipped or unmatched test cases cannot establish a pass. A successful test run does not establish deployment.

Growing next.

Exacly is open source and at 0.x. The specification and tools are evolving.

Use today

Validate config. Refresh state from test results. Trace purpose and inspect change impact. Browse a model, connect an agent, or evaluate a readiness policy in CI.

Use the GitHub Action

Plan verification work

exacly plan proposes verification work for a selected target and policy. It distinguishes known failures, missing evidence and missing observation bindings.

Planning is available in stable Exacly 0.6.0. The 0.7.0rc1 candidate adds separately authorized task dispatch, isolated local execution and reviewed Git handoff. Remote source publication and unattended end-to-end automation remain future work. The PR “plan” view still reports model changes and potential impact.
