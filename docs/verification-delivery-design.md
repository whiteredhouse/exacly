# Independent verification, scoped assessments, and policy gates

The user authorized all three stages as separate PRs on 2026-10-26. See [research](verification-delivery-research.md). Implement in a stack, retaining Python 3.12 and the existing dependencies.

1. **Independent verification.** Rule 7.8 requires an implementer and applicable evidence separately for each positive delivery or verification claim. Verification has no delivery prerequisite. Existing failed/skipped/missing semantics remain. Exceptions must still be tested against actual unsupported claims.
2. **Scoped assessment projection.** Add optional `subject` to assessments, with `model_revision` required and optional `revision`, `builds`, `release`, `environment`, `platform`. `builds` maps component names to identity-field maps, as manual QA already does. Introduce a validated target with required `context`, `model_revision`, and at least one of `revision` or `builds`; optional scope fields are `release`, `environment`, `platform`. Exact identities match; revisions allow the existing Git abbreviation rule. Every identity requested by a target must be established by the observation. A more narrowly scoped observation cannot establish a broader claim. Delivery environment defaults to the selected context when omitted; verification without environment is a source-only claim. Other scope must be selected explicitly. A revision-only result does not establish artifact/build or environment verification. Model revision is independently checked. Preserve observations; report exclusion reasons and evidence validity. `query.assess(model, record, target)` returns target, per-dimension states, applicable and excluded assessments, and missing bindings. Required bindings must all contribute applicable results. No observations means verification not checked and delivery not observed, as derived labels. `exacly assess RECORD --target FILE` exposes text/JSON. Existing queries use a conservative guard for refresh test results from another revision, so they cannot combine unit A and integration B. Manual QA writes subject from its target. Refresh writes model/source revision independently on each assessment; distribution also names its environment. Legacy refresh tests can establish only their documented tested revision; generic legacy delivery cannot establish an implementation identity. No heuristic extraction from evidence prose.
3. **Policy gates.** Add a read-only `exacly gate --policy FILE --target FILE` command, backed by `policy.evaluate(model, policy, target)`. Policy documents require `name`, `version`, and nonempty `requirements`: each names a Requirement record and nonempty required dimensions (`verification`, `delivery`). Each dimension evaluates scoped assessment results from stage 2. Satisfied means all requested positive states; not satisfied means an applicable negative result; unknown means absent, expired, ambiguous or unsupported evidence. Negative dominates unknown. Nonconforming input blocks with unknown and links findings. CLI exits 0 satisfied, 1 not satisfied or unknown, 2 invalid policy/target/input. Report policy identity, target, as-of date, per-check reasons and evidence; no state mutation. It evaluates observed prerequisites and does not execute deployment or infer production correctness. Schema validation rejects unknown fields and duplicate checks/dimensions. No general expression language, policy engine, or event store.

Each PR includes regression tests, documentation, and required `mise run check` verification. New commands accept explicit dates for deterministic evaluation. Structured targets and policy documents are separate inputs, stored outside model folders. These additions do not rename existing stored states. Subjects with only model revision cannot establish a target's implementation identity. Reobserving tests replaces that source as before; observing a different source preserves the original subject and timestamps.
